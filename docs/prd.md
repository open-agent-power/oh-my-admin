# oh-my-admin 功能瘦身——功能删除 PRD

## 1. 项目背景

当前项目基于 ContiNew Admin 进行二次开发。为了减少项目中与实际业务无关的冗余功能，降低系统复杂度、维护成本和代码体积，需要对现有管理后台进行功能瘦身。

本次改造以现有系统功能为基础，**仅删除明确指定的功能模块及其相关实现，不影响系统核心认证、用户权限、组织管理及其他未列入删除范围的功能。**

本 PRD 用于明确本阶段需要删除的功能范围、删除边界以及验收标准，作为开发和 AI Coding Agent 执行改造的依据。

------

## 2. 改造目标

### 2.1 核心目标

对系统中当前不需要的功能进行彻底移除，包括：

- 前端页面
- 菜单及路由
- 后端 Controller
- Service
- Mapper
- DTO / VO / Query
- 数据库表及相关 SQL
- 定时任务
- 配置项
- 权限标识
- 字典
- API
- 前端 API 请求封装
- 类型定义
- 国际化文本
- 菜单初始化数据
- 与被删除功能强耦合的无用代码

### 2.2 改造原则

1. **只删除明确列出的功能。**
2. **不得误删核心登录、认证、权限功能。**
3. **删除功能后不得留下无效菜单、路由、接口和配置。**
4. **删除后项目应能够正常启动和编译。**
5. **数据库中与已删除功能完全无关的核心数据不得删除。**
6. 对存在依赖关系的代码，应先分析调用链，再进行删除。
7. 不为了“代码看起来更干净”而扩大删除范围。

# 16. 技术实现要求

本次改造不能只做“隐藏菜单”。

对于删除的功能，应按照完整功能链路进行清理：

```text
前端页面
  ↓
路由
  ↓
菜单
  ↓
权限
  ↓
API
  ↓
Controller
  ↓
Service
  ↓
Mapper
  ↓
Entity / DTO / VO
  ↓
数据库表
  ↓
配置
  ↓
依赖
```

需要根据实际项目结构判断哪些代码属于被删除功能。

### 禁止出现

删除菜单但保留：

- 后端 API
- Controller
- Service
- 数据库表
- 定时任务
- 无用配置
- 前端 API
- 无用依赖

导致项目产生大量“孤儿代码”。

# 17. AI Coding Agent 执行要求

如果由 AI Coding Agent 执行本次改造，应遵循以下流程：

### 第一步：分析

先扫描项目结构，确定：

- 前端项目结构
- 后端项目结构
- 菜单结构
- 路由结构
- 权限结构
- 数据库迁移 SQL
- 配置文件
- 模块依赖关系

### 第二步：建立删除清单

对每个待删除功能建立：

```text
功能
├── 前端页面
├── 路由
├── API
├── 后端 Controller
├── Service
├── Mapper
├── Entity
├── DTO / VO
├── 数据库
├── 权限
├── 菜单
├── 配置
└── 依赖
```

### 第三步：执行删除

按照依赖关系删除代码。

### 第四步：清理引用

重点搜索：

- import
- API 调用
- 类型引用
- 菜单引用
- 权限标识
- 配置引用
- 数据库表引用
- 定时任务引用

避免删除后出现编译错误。

### 第五步：验证

至少完成：

- 前端构建
- 后端编译
- 项目启动
- 登录测试
- 用户管理测试
- 角色权限测试
- 菜单测试
- 部门管理测试
- 删除功能访问测试

# 18. 验收标准

## 18.1 前端验收

删除的功能不应再出现在：

- 左侧菜单
- 路由
- 页面
- 设置页面
- 个人中心
- 仪表盘
- 按钮权限
- 操作入口

## 18.2 后端验收

删除功能对应的：

- Controller
- Service
- Mapper
- DTO
- VO
- Query
- Entity

应在确认无其他业务依赖后清理。

## 18.3 数据库验收

对于完全属于删除功能的数据表：

- 删除对应数据库表；
- 删除相关初始化 SQL；
- 删除数据库迁移脚本中的无效内容；
- 删除无效索引和关联配置。

但如果某张表同时被其他保留功能使用，**不得直接删除**。

## 18.4 核心功能验收

删除完成后必须保证：

```text
登录
  ↓
认证
  ↓
Token
  ↓
权限
  ↓
用户
  ↓
角色
  ↓
菜单
  ↓
部门
```

这一核心链路正常。

# 19. 风险与注意事项

### 19.1 不得误删登录

**客户端配置 ≠ 登录功能。**

删除客户端多端认证管理时，不得删除：

- 登录接口
- Token 生成
- Token 校验
- 登录配置
- 登录安全机制

### 19.2 不得误删短信相关的全部认证能力

本次删除的是：

> **短信配置 + 短信日志**

如果项目中的验证码、安全校验等功能仍然依赖短信能力，需要分析依赖后再处理。

### 19.3 不得直接按照关键词全局删除

例如：

```text
client
token
task
message
user
login
```

这些关键词可能同时被其他核心功能使用。

必须根据实际调用关系判断，而不是简单全局删除。

### 19.4 不得扩大需求范围

本 PRD 没有要求删除的功能，原则上不得主动删除。

# 20. 最终目标

本次改造完成后，系统应成为一个更加精简的 Admin 基础框架：

```text
保留核心能力
│
├── 登录 / 认证
├── 用户管理
├── 角色管理
├── 菜单管理
├── 部门管理
├── 权限管理
├── 个人中心基础功能
├── 系统基础配置
└── 其他未明确删除的业务能力

删除冗余能力
│
├── 仪表盘最新公告
├── 仪表盘动态
├── 微信第三方账号绑定/解绑
├── 消息中心
├── 短信配置
├── 客户端多端认证管理
├── 短信日志
├── 应用管理
├── 租户管理
├── 租户套餐
├── 任务管理
├── 任务日志
└── 代码生成
```

**本阶段核心原则：精确删除、完整清理、保持核心认证和权限体系稳定，不扩大删除范围。**
